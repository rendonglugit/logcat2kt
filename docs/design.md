# logcat2kt：logcat 日志 → 可折叠 JSON / Kotlin data class

一个单文件网页工具：粘贴 logcat 里复制出来的任意几行，右边给出**可折叠的树视图**和对应的 data class。

支持三种输入形态：**JSON**、**Kotlin/Java toString**、**Protocol Buffer**（TextFormat 与二进制 hex）。

打开方式：双击 `index.html`。无依赖、离线可用、不联网。

---

## 一、痛点拆解

这个需求本质上是四件事串在一起，每一件单独看都不难，连起来就变成了每天十几分钟的机械劳动。

| 环节 | 实际发生的事 | 手工代价 |
|---|---|---|
| ① 日志被截断 | logcat 单条上限约 4KB，超了会被系统切成多条，每条重新带上 `时间 pid-tid/包名 级别/Tag:` 前缀 | 复制出来是一堆碎片，要肉眼找接缝 |
| ② 碎片拼接 | 接缝经常落在字符串中间，看不出哪行接哪行 | 逐行删前缀、手工对齐，容易拼错引号 |
| ③ 结构化 | 拼回去是一整行几 KB 的字符串 | 得再开一个在线格式化网站，还要担心贴的是业务数据 |
| ④ 写 data class | 字段十几个、嵌套三四层 | 对着内容一个个敲，命名转换、可空、类型全靠人脑记 |

联调期一个接口来回改，这个动作一天重复五到二十次。**高频 + 单次收益明确 + 零学习成本**，这是典型值得做小工具的场景。

反过来讲，如果一周只碰两次接口，手搓更快，就不值得。

## 二、可行性分析

### 1. 前缀剥离

logcat 的复制格式不统一，至少要覆盖这几种：

```
2026-10-26 17:08:10.123 12345-12401/com.example.app D/OkHttp: {...}
10-26 17:08:10.123  1234-5678/com.example.app D/OkHttp: {...}
10-26 17:08:10.123 1234 5678 D/OkHttp: {...}
D/OkHttp: {...}
D/OkHttp( 1234): {...}
2026-10-26 17:08:10.123  1234-1234  OkHttp  com.example.app  D  {...}   ← AS 新 Logcat 表格复制
17:45:15.895  D  {...}                                                  ← 只有时间+级别，无 tag
```

最后一种容易漏掉：长文本日志的续行经常只有 `时间  级别  内容`，没有 pid/tid/tag。识别不了的话时间戳会被当成内容拼进去，`17`、`15.895` 直接变成字段名。

做法是正则数组按信息量从多到少依次尝试，第一个命中的就是结果。注意 `1234-5678/com.pkg` 是一体的（`/` 不是空格），这里最容易写错。

兜底原则：**匹配不上就整行当内容**，不猜。

另外还会剥掉长文本日志框架的包装标记：

```
@long-text:"[response]..." <long_text_quote>[response]:{...}</long_text_quote>
```

`@long-text:"..."` 和 `<long_text_quote>` 标签是框架加的，不是业务数据。

### 2. 截断识别与拼接（核心）

截断后的续条有两种形态，都要处理：

- **带前缀的独立 chunk**：每条都是完整的一行，tag 相同
- **无前缀的折叠行**：AS 把同 tag 连续行折叠后，续行可能没有前缀

判定不能靠"看起来像"，要靠状态：对每段内容做一次**括号 + 引号平衡扫描**（跳过字符串内部的括号），未闭合就说明话没说完。

拼接条件：`同 tag + 上一条未闭合`。两个条件都满足才拼，避免把两条独立日志误合并。

拼接时有个容易忽略的细节：**断在字符串中间就直接接上，断在 token 之间要补换行**。早期版本一律直接拼，结果多行 TextFormat 被压成一行，protobuf 的多行判定直接失效。

### 2.1 中间丢段（比截断更难缠）

这是实际踩到的问题。logcat 缓冲溢出时，丢的往往不是尾巴，而是**中间一整段**：

```
..."accountDisabled":false,          ← 第一行到这里
[系统丢了 "rankBadges":[{"topN":1,"rangeType":"GLOB]
pe":"GLOBAL","rankType":"honor",...  ← 续行从半个 key 开始
```

直接拼起来就是 `..."accountDisabled":false,pe":"GLOBAL",...`，`pe` 会被当成新字段名，后续所有 key 都跑到错误的层级——生成的类里会出现 `17`、`15.895` 这种字段名，`lang`/`groupInfo`/`subs` 反而全丢。

处理分两步：

**① 判定**。拼接缝隙满足「左端停在 token 边界（`,` `{` `[` `:`）+ 右端不是合法 token 起始」时，判定为丢段。特别是右端形如 `xxx"`（字母后面直接跟引号），这是残缺 key 尾巴的铁证。

**② 对齐**。难点在于**残片开头的 `"` 也丢了，引号奇偶性整体反了**，用括号深度扫描会全盘错位（这个方案试过，失败）。

改用结构锚点：缺失段一定吞掉了数组的 `[`，所以残片里第一个 `],"` 或 `]}` 就是数组真正的结束点，之后即回到外层结构。跳过残片接到那里，再处理拼接处的重复逗号。

效果：上面那个例子修复后只丢 `rankBadges` 一个字段，`lang` 到 `subs` 全部恢复，`activity` 从 74 个字段恢复到 111 个，且没有任何垃圾字段名。

**局限**：如果缺失段里没有数组（纯对象丢段），只能退回到 `},"` 锚点，准确性下降；找不到任何锚点时整段丢弃，等于截断。状态栏会显示「日志缺失 N 处已跳过」，不会静默处理。

### 3. 数字精度

这是容易被忽略但很致命的一点。JS 的 `JSON.parse` 会把 `9007199254740993123` 变成 `9007199254740993000`——订单号、用户 ID 这类 19 位数字直接报废。

所以没有用 `JSON.parse`，自己写了一个递归下降 parser，数字只保留原文 `raw` 字符串，类型判断（Int / Long / Double）也从原文判断。

### 4. 非标准 JSON

真实日志里跑出来的东西经常不是合法 JSON：

| 情况 | 例子 |
|---|---|
| 尾逗号 | `{"a":1,"b":[1,2,],}` |
| 单引号 | `{'a':1}` |
| key 无引号 | `{a:1,b:2}` |
| Kotlin toString | `Data(code=0, list=[Item(id=1)])` |
| 尾部被吃掉 | `{"a":1,"b":"xx` |
| 无逗号分隔 | `{ id: 1\n nickname: "x" }` |

parser 本身是容错的：读不到闭合符就带着已解析的部分返回，而不是抛异常。这样"尾部截断"天然就被处理了——能拿到多少字段算多少。

### 5. Protocol Buffer

这里要分清三种形态，它们的处理方式完全不同：

#### 5.1 JSON 映射（`JsonFormat.printer()`）

就是标准 JSON，已经天然支持。只有一个坑：protobuf 的 `int64` 在 JSON 映射里是**字符串**（`"880012345678"`），工具会推成 `String` 而不是 `Long`。这是 proto 的规范要求，不算工具的错。

#### 5.2 TextFormat（`proto.toString()` 的输出）—— 最常见

```protobuf
user {
  id: 1008611
  nickname: "张三"
  tags: "music"
  tags: "game"
  status: STATUS_ACTIVE
  profile {
    level: 12
  }
}
```

这是 `Log.d("pb", proto.toString())` 的标准输出。语法要点：

| 语法 | 处理方式 |
|---|---|
| `key: value` | 标量字段 |
| `key { ... }` / `key < ... >` | 嵌套 message，递归解析 |
| `key: [1, 2, 3]` | 短格式列表，展开成多条重复字段 |
| 同一个 key 出现多次 | **合并成数组**（这就是 proto 的 repeated 语义） |
| 不带引号的标识符 | 识别为 enum 值（`STATUS_ACTIVE`） |
| `#` 开头 | 注释，跳过 |

关键点：**repeated 字段是靠"重复出现"表达的，不是靠数组**。所以必须做重复 key 合并，否则 `tags` 会出现两次、生成两个同名属性。

#### 5.3 二进制（`proto.toByteArray()` 的 hex dump）

没有 `.proto` 也能解，因为 wire format 是自描述的：

```
08 E9 07 12 02 68 69 1A 02 08 01
│  │     │  │  └─ "hi"
│  │     │  └─ wire type 2 (length-delimited), 长度 2
│  │     └─ field 2
│  └─ varint 1001
└─ tag: field 1, wire type 0
```

解码器按 wire type 分支处理：

| wire type | 含义 | 处理 |
|---|---|---|
| 0 | varint | 用 BigInt 读，避免 64 位溢出 |
| 1 | 64-bit fixed | 启发式：先当 int64，不合理再当 double |
| 2 | length-delimited | 先试 UTF-8（能读成文本就当 string），否则递归当嵌套 message，都不行就当 bytes |
| 5 | 32-bit fixed | 同上，int32 / float |

字段名只能是 `field_1`、`field_2`——**没有 `.proto` 就没有真实字段名**，这是固有限制。

#### Protobuf 的固有限制（做之前就该知道）

| 限制 | 说明 |
|---|---|
| 没有字段名 | 二进制解码只能给 `field_N`，需要自己对回 `.proto` |
| repeated 单值无法区分 | `tags: "music"` 只出现一次时，分不清是 `optional string` 还是 `repeated string`，工具按标量处理 |
| packed repeated 会退化 | `repeated int32` 打包后是一段字节，无 schema 无法识别，会显示成 hex |
| enum 推不出枚举类 | 只能给 `String`，不会生成 `enum class` |
| string / bytes / 嵌套 message 三选一靠猜 | length-delimited 的语义歧义，无 schema 无解 |

### 6. 类型推断

| 输入 | 输出 | 规则 |
|---|---|---|
| `0` / `1001` | `Int` | 在 int32 范围内 |
| `880012345678` | `Long` | 超出 int32 |
| `12.50` | `Double` | 有小数点就 Double，不猜 Float |
| `"张三"` | `String` | 不因为长得像数字就转 |
| `[]` | `List<Any>` + 注释 | 空数组推不出元素类型，标注出来 |
| `null`（样本里全是 null） | `Any?` + 注释 | 同上，不瞎猜 |
| 数组元素字段不一致 | 字段取并集，缺失的标可空 | 多次响应合并时尤其需要 |
| `create_time: 1729934890123` | `Long` | 字段名命中时间戳特征，即使值在 int 范围也升 Long |

### 7. 命名冲突（踩过的坑）

生成代码最容易翻车的地方不是类型，是名字：

- **字段 `list` 生成 `data class List(...)`** → 直接把 Kotlin 的 `List` 遮蔽掉，整份代码编译报错。对策：`List/Map/Set/String/Int/...` 这批标准类型名一律加 `Item` 后缀（`List` → `ListItem`）
- **`activity` 生成 `data class Activity`** → 和 `android.app.Activity` 撞名。同一批黑名单里也放进了 `Activity/Fragment/View/Context/Intent/Bundle/Service/...` 这些 Android 高频类，生成 `ActivityItem`
- **硬关键字**：`in`、`is`、`object`、`val` 做属性名必须加反引号
- **软关键字不转义**：`data`、`field`、`it` 这些是合法的属性名，转义了反而难看
- **注解只在改名时加**：`user_id` → `userId` 需要 `@SerializedName`，`code` → `code` 不需要

### 8. 可折叠视图

从"一段高亮文本"改成"一棵 DOM 树"，技术上是纯渲染层重构，没有算法风险。

要点：

- 每个容器节点（对象/数组）渲染成 `节点头行 + 子节点容器 + 结束行` 三段
- 折叠时隐藏后两段，头行原地显示摘要 `{ … } 5 个字段`
- 缩进用 `border-left` 画引导线，层级关系一眼能看出来
- 折叠状态存在 DOM class 上，不重排、不重算，点击零延迟
- 超过 6000 个节点自动降级为纯文本，避免大 JSON 卡死

复制按钮走的是另一条路：从 AST 重新生成纯文本，不受折叠状态影响。

## 三、工具设计

处理管线是一条直线，每步职责单一：

```
原始文本
  └─ ① 行解析      正则剥前缀，识别 tag / level / 时间戳
      └─ ② 条目合并  括号平衡扫描，同 tag 未闭合则拼接
          └─ ③ 结构识别  四种策略按序尝试（见下）
              └─ ④ 宽容解析  → 统一 AST
                  ├─ ⑤ 可折叠树渲染
                  └─ ⑥ 类型推断 → 按 tag 分组 → ⑦ Kotlin 生成
```

**结构识别的优先级**（顺序有讲究，错了会互相抢）：

```
① Kotlin toString   ^Name(          → 避免被内部的 [1,2] 列表抢走
② protobuf TextFormat  ^ident[:{<]  → 必须在 JSON 之前，否则 user { 会被当成 JSON
③ JSON              { / [           → 最常见的路径
④ protobuf hex      纯 hex 串        → 兜底
```

另有一条**扁平 TextFormat 兜底**：如果逐条都提取不到，但整组日志每行都是 `key: value`（没有 `{}`），就按 tag 把所有行重新拼起来再解析。这是 `Log.d("pb", "id: 1")` 逐字段打印的常见写法。

**几个有意的设计选择：**

- **按 tag 分组，而不是全部合并。** 粘贴一整屏日志时可能五六个接口混在一起，全合并会得到字段全可空、互相污染的巨型类。现在各生成一套，类名用 tag 前缀区分（`OkHttpResponse`、`ApiResponse`）。
- **默认全部可空 + `= null`。** 最安全的反序列化姿势——字段缺失不崩，字段多出来也不崩。
- **扁平输出，不嵌套。** 所有 data class 平铺，Gson / kotlinx 都能直接用。
- **状态栏说人话。** 显示"日志行 3 / 条目 1 / 结构 1 / 格式 JSON / 自动拼接 1 次 / **日志缺失 1 处已跳过** / tag Api"，能立刻确认工具理解得对不对。丢段是黄色提示，不会静默处理。

## 四、使用

1. 双击 `index.html`
2. 从 logcat 里框选复制（多选几条没关系，混着别的日志也行）
3. 粘贴到左边
4. 右边看结果，点 `▾` 折叠/展开，切到 Kotlin 标签页复制

**折叠操作**：点节点左侧的三角折叠单个节点；顶部「全部折叠 / 全部展开」批量操作。折叠后原地显示 `{ … } 3 个字段`。

顶部四个选项：

| 选项 | 说明 |
|---|---|
| 根类名 | 顶层类名，默认 `Response`；多组时会拼上 tag 前缀 |
| 注解 | 无 / Gson / kotlinx.serialization / Moshi |
| 可空策略 | 全部可空（推荐）/ 按样本推断 / 全部非空 |
| 命名 | 转 camelCase / 保持原样 |
| 时间戳字段用 Long | 名字像时间的整数字段升为 `Long` |

`index.html#kotlin` 打开会直接落在 Kotlin 标签页，可以收藏成书签。

**看到状态栏出现「日志缺失 N 处已跳过」（黄点）时**，说明这段日志中间被系统丢了一块，缺失段里的字段确实找不回来了，但断点前后的结构已经自动对齐。如果正好是你要的字段，重新抓一次日志更靠谱。

## 六、如果要做重

当前形态（单文件网页）是投入产出比最高的：零安装、跨平台、随手能改。真要往下走，按价值排序：

| 方向 | 价值 | 成本 |
|---|---|---|
| **AS Logcat 过滤器插件** | 最高——连复制粘贴都省了，选中即转 | 高，要写 IntelliJ 插件 |
| **CLI**：`adb logcat \| logcat2kt` | 中——适合长时间抓包后批量处理 | 低，parser 是纯逻辑可直接移植到 Node |
| 拖入 `.proto` 文件反查字段名 | 中——解决二进制解码只有 `field_N` 的问题 | 中，要写 proto 解析 |
| 反向：Kotlin 类 → JSON 样本 | 低——造 mock 数据时偶尔用 | 低 |

值得强调的是：**parser 和生成器是纯函数，没有一行 DOM 依赖**。想搬到 CLI、插件、或者接进 CI，直接拿 `parseLog / extractNodes / parseLoose / parseProtoText / decodeHexDump / typeOf / genKotlin` 这几个函数就行。
